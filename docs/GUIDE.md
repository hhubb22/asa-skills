# 使用指南

这份指南面向第一次使用 Agent 工作流的同事，也可以直接作为推广分享的大纲。

## 解决什么问题

很多人已经在用 Agent 写代码，但常见三类问题：

- **Agent 没做成我想要的**：需求没说清，Agent 用自己的默认值补上了空白。
- **改出来的东西不敢用**：没有设计、没有验证，出了问题不知道从哪查。
- **知道概念，落不了地**：听说过"先写规格再写代码"，但不知道每一步具体怎么做、什么时候可以跳过。

这套 skills 把一条可执行的工作流拆成 14 个通用核心能力，另有 2 个面向公司评审流程和隔离实验室的扩展。每个能力是一份中文指令，装进你常用的 Agent 后，用一句话就能调用。

## 四个核心概念

**1. 主路径**

```
对齐 → 行为规格 → 技术设计 → 拆分任务 → 实施 → 审查
align   write-product-spec  write-tech-spec  to-tasks  implement-specs  code-review
```

每一步都有跳过条件：小改动直接做，局部改动不用写设计，一个会话能完成的不用拆任务。不确定从哪开始时，调用 `work`，它会选好路径并告诉你。

**2. 长期文档与过程文件分开**

| 类型 | 内容 | 放在哪里 |
|---|---|---|
| 长期文档 | 行为规格、技术设计、ADR、术语表 | 仓库 `specs/<特性>/`，与代码同一提交 |
| 过程文件 | 需求对齐、任务清单、进度、交接、实验室请求、TR 草稿 | `~/.agents/work/<项目>/<特性>/`，不进仓库 |

**3. 授权边界**

- 调查、设计、审查只交付报告和文档，不改代码。
- 你说"实现"，Agent 才改代码，并且在范围内自己完成验证和修复。
- 提交、推送、对外发消息、操作实验室设备，都需要你明确同意。

**4. 项目配置**

核心 skill 不绑定任何领域。每个项目的差异，例如评审文档是什么、需求怎么编号、有没有隔离的验证环境，写在过程区的 `PROJECT.md` 里。没有这份文件时按通用默认工作。

## 开始前准备

**每位使用者**

1. 准备环境：Node.js，能访问 GitHub 和 npm。在公司网络下先试一次安装。
2. 安装核心 skill；做 PICOS 项目的同事再装扩展（命令见下）。
3. 为当前项目创建 `~/.agents/work/<项目>/PROJECT.md`。模板在 `work` 的 assets 目录里；PICOS 项目可以直接复制仓库中的 [示例](../examples/project-config-picos.md)。
4. （可选）把 `~/.agents/work/` 初始化为个人 Git 仓库，保留过程文件的历史。

**团队约定**

5. 确认长期文档的位置，默认 `specs/<特性>/`，与代码同一提交。产品仓库里新增文档目录需要团队认可。

## 安装

```bash
# 查看全部能力
npx skills add hhubb22/asa-skills --list

# 核心：任何项目都适用
npx skills add hhubb22/asa-skills --skill work --skill align --skill write-product-spec --skill write-tech-spec --skill to-tasks --skill implement-specs --skill code-review --skill diagnose-bugs --skill research --skill domain-modeling --skill handoff --skill wait-what --skill to-questionnaire --skill skill-doctor -g -a codex -a cursor

# 扩展：公司 TR 评审流程与隔离实验室（开发侧）
npx skills add hhubb22/asa-skills --skill write-tr --skill lab-request -g
```

`-a` 后面换成你使用的 Agent。调用方式随宿主不同：Codex 用 `$work`，Cursor 用 `/work`，Pi 用 `/skill:work`，也可以直接用自然语言说"用 work 处理……"。装完后新开一个会话。

## 典型用法

下面的句子可以直接复制，把尖括号部分换成你的内容。

**新特性，从想法开始**

```text
用 align 确认一下我的需求：<描述>
（确认后）根据 ALIGN.md 写行为规格
（需要时）根据 PRODUCT.md 写技术设计
用 to-tasks 拆任务
按 TASKS.md 实现 T01，跑完测试告诉我结果
用 code-review 检查当前修改，包括未跟踪文件
```

**新特性，已经有 TR**

```text
这是 TR1 的内容：<从飞书复制>。用 align 对照 TR 复述，TR 没写的地方列为假设
```

**先验证可行性**

```text
用 work：我不确定 <问题>，先做快速验证，不要写正式文档
```

**修 bug**

```text
用 diagnose-bugs 查一下：<现象，出现频率，相关日志>
```

**读代码或标准**

```text
用 research 查一下 <问题>，给出处
```

**需要上机验证**

```text
用 lab-request 为 <验收项> 生成实验室请求单
（用你习惯的方式执行请求单：交给实验室里的 Agent、跑脚本或手动操作，拿回结果后）
这是 LAB-<特性>-01 的回传结果：<粘贴>。判断是否通过
```

**准备 TR 评审**

```text
用 write-tr 根据 PRODUCT.md 和现有代码起草 TR1
```

**换会话继续**

```text
用 handoff 写交接，我要换个会话继续
```

## 常见问题

**会不会乱改代码？** 不会。只有你明确说实现，Agent 才会改代码；审查和设计默认只交付文档。

**要写很多文档吗？** 不用。小改动直接做；只有行为需要约定时写行为规格，只有跨模块或有取舍时写技术设计。

**和 TR 什么关系？** TR 是评审时点的快照。开发前它是输入，开发后以仓库里的文档为准；偏离通过 TR 的基线后变更记录回报。`write-tr` 可以从工程文档起草 TR。

**开发环境连不上实验室怎么办？** 用 `lab-request` 生成自包含的请求单，写清测什么、怎么判断、带回什么，以及执行约束。用你方便的方式执行，再把结果粘贴回来判定。

**支持哪些工具？** 遵循标准 SKILL.md 格式的 Agent 都能读取。已按文档核对 Codex、Pi、Cursor；其他工具请先试装。

**效果有数据吗？** 还没有。仓库里有 31 个行为案例和 90 条触发测试，尚未在真实环境中跑过。欢迎试用后反馈。

## 推广分享大纲

建议 30 分钟。

| 时间 | 内容 | 要点 |
|---|---|---|
| 3 分钟 | 问题 | 上面三类问题，请大家对号入座 |
| 5 分钟 | 主路径 | 一张图讲清六步和跳过条件；强调"不是流水线" |
| 5 分钟 | 核心概念 | 长期文档与过程文件分开；授权边界；项目配置 |
| 10 分钟 | 案例 | 用一个真实特性走一遍，见下 |
| 4 分钟 | 安装与上手 | 现场安装，创建项目配置，跑一次 `align` |
| 3 分钟 | 下一步 | 收集反馈；内部 skills 共享平台作为第二阶段 |

### 案例讲述框架

用一个已经完成的特性回顾，按主路径逐步讲清"每一步产出了什么、省了什么"。尖括号部分按实际情况填写。

1. **对齐**：最初的需求是 <…>；复述中暴露出的关键假设是 <…>，纠正后避免了 <…>。
2. **快速验证**：在 <环境> 中先验证了 <可行性问题>，结论是 <…>。
3. **规格与设计**：行为规格定义了 <关键行为>；技术设计在 <方案 A/B> 之间选择了 <…>，理由是 <…>。
4. **实施与验证**：开发环境用 <测试方式> 覆盖了 <…>；上机验证了 <…>。
5. **评审材料**：以实际实现为依据起草 TR，评审时 <效果>。
6. **收获**：<时间、返工、质量方面的具体变化>。

讲案例时展示真实产物：ALIGN.md 的假设表、PRODUCT.md 的一条行为要求、一张实验室请求单。产物比描述更有说服力。
