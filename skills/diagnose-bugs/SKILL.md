# Diagnose bugs

用可重复的信号定位根因。没有反馈回路时读代码猜原因，是这个 skill 要防止的做法。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。构造回路时参考 [回路清单](references/feedback-loops.md)。

复制下面的清单，逐项推进：

```
- [ ] 1. 反馈回路：一条已运行过、能稳定复现症状的命令或步骤
- [ ] 2. 复现并最小化
- [ ] 3. 3–5 个可证伪的假设，已展示给用户
- [ ] 4. 逐个验证假设，定位根因
- [ ] 5. 回归测试与修复
- [ ] 6. 清理与报告
```

## 1. 建立反馈回路

这是最关键的一步，值得投入最多精力。回路满足四个条件才算完成：

- **能变红**：走真实的出错路径，断言用户描述的那个症状，而不是"没有崩溃"。
- **稳定**：每次运行结论相同。偶发问题要把复现率提高到可调试的程度，例如循环触发、加压、收窄时间窗口。
- **快速**：秒级优于分钟级。
- **可执行**：Agent 能直接运行；只能在开发环境无法直达的环境中复现时，用 `lab-request` 生成请求单，由用户带回结果。

已经运行过一次并看到失败输出，才进入第 2 步。确实无法建立回路时，列出尝试过的方法，向用户要现场材料或复现环境，例如日志、请求记录、抓包、core dump。

## 2. 复现并最小化

- 确认复现的是用户描述的症状，而不是附近另一个问题。
- 一次删一个输入、配置或步骤，每次删除后重跑回路，只保留去掉就不再复现的部分。最小复现会成为回归测试。

## 3. 提出假设

一次提出 3–5 个假设并排序。每个假设写成可证伪的形式："如果原因是 X，那么改变 Y 会让问题消失。"写不出预测的假设，要么具体化，要么放弃。

先把排序后的列表展示给用户：用户常有领域知识能立刻调整排序。用户暂时不在时，按自己的排序继续。

## 4. 验证与定位

- 每个探针对应一个假设的预测，一次只改一个变量。
- 优先用调试器；其次在能区分假设的边界处加日志。
- 调试日志统一加前缀，例如 `[DBG-a4f2]`，方便最后清理。
- 性能问题先测基线，再二分定位。

## 5. 修复与回归测试

在合适的接缝处，先把最小复现写成失败的测试，再修复，看它通过，最后用第 1 步的原始回路复验。

找不到合适的接缝本身就是一个发现：说明当前结构无法锁住这个缺陷。在报告中写明。

## 6. 清理与报告

- 原始回路不再复现；回归测试通过，或说明无法添加的原因。
- 删除所有带前缀的调试日志和一次性原型。
- 日志、抓包和输出中的密钥、口令和令牌一律脱敏。
- 报告根因、被证实的假设、修复内容和验证结果，写进提交说明，供下一个排查者参考。
