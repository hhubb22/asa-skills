# 反馈回路清单

按代价从低到高排列。优先选能在开发环境运行的回路，必须上机时再用实验室回路。

## 开发环境

1. **单元或集成测试**：在能触达缺陷的最浅接缝处写失败测试，例如协议状态机、报文解析、配置校验。
2. **报文回放**：把抓到的报文（pcap）或事件序列保存下来，单独送入解析或处理路径。
3. **命令行加固定输入**：用固定配置或输入运行工具，与已知正确的输出对比。
4. **最小化运行环境**：只启动相关进程，依赖用桩替代，例如用 Linux 内核 macsec 或 veth 对代替交换机端口。
5. **差分比较**：同一输入分别跑旧版本和新版本，或软件实现和硬件实现，对比输出。
6. **二分**：问题出现在两个已知版本之间时，脚本化"构建 → 检查"，再用 `git bisect run`。
7. **随机输入**：偶发的错误输出用大量随机输入循环触发，寻找规律。

## 实验室

8. **设备脚本**：在设备上执行配置与 show 命令，比较输出与预期。通过 `lab-request` 生成请求单。
9. **计数器与跟踪**：芯片或 SDK 计数器、调试跟踪，加上时间戳。
10. **两台设备拓扑**：互通、协商、故障恢复类问题，在直连拓扑上复现。

## 偶发问题

目标是提高复现率，而不是追求一次干净复现。循环触发上百次、并发、加压、收窄时间窗口。复现率达到能区分假设的程度即可开始第 3 步。

## 现场材料

无法复现时向用户索取，并说明需要哪一段：

- pcap：注明抓包位置和时间范围。
- show tech 或运行配置：注明设备、镜像版本和采集时间。
- 日志：注明进程和时间范围。
- core dump：附上对应的镜像和符号文件版本。

所有材料先脱敏再引用。
