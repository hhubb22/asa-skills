# Implement specs

把已有依据转为经过验证的实现，不另建一套项目管理流程。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。仅在长任务需要跨会话状态时使用 [进度模板](assets/PROGRESS.template.md)。

## 开始

核对当前任务、已确认设计、相关项目规则和工作区状态。依据可以是规格、issue 或已经明确的讨论，不要求固定文件名。重大语义尚未决定时，先完成不依赖它的调查和准备，再给具体待决方案。

只读取受影响模块的实现、测试和约束。保留用户已有修改；必要时使用隔离工作区，避免为了整洁自动 stash、reset 或重写历史。

## 实施与反馈

按可以独立验证的变化推进，复用项目现有测试和生成工具。回归修复能先构造有效失败用例时先做；没有完整硬件环境时利用日志、模拟、重放或局部验证，同时保留覆盖限制。

在批准范围内自行完成实现细节和必要修复，不逐步请求许可。发现外部行为、兼容性或模块职责需要改变时，准备修订和影响说明；不要悄悄将实现偏差写回规格当作批准。

修改类型、协议或依赖后，按项目规定同步生成文件、契约文档和锁文件。事实性同步与语义变更分开处理；只更新相关内容。

## 验证与结束

执行项目要求及本次变化最相关的验证；风险跨越共享模块时再扩展。每次测试注明实际命令、结果和必要环境。修改后受影响的结论需要重新验证；无新变化、无新证据时不重复已通过检查。

审视最终 diff 的正确性与范围。复杂差异可以使用已安装的 `code-review`，或按项目规则审查；不把加载审查 skill 当成强制仪式，也不把编译通过等同于功能正确。

完成报告包含实际改变、关键行为的验证、未验证范围与阻塞。提交/推送等操作使用已有授权；没有授权时交付工作区与命令结果，不自动发布。
