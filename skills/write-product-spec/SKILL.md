# Write product spec

交付使用方能够理解和检验的行为约定。使用方可以是人、API 调用者、协议对端或其他模块。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。写文档时按需读取 [写作约定](references/technical-writing.md)；新文档采用 [模板](assets/PRODUCT.template.md)，需要校准粒度时看 [示例](references/example-product.md)。

## 依据与范围

先利用当前需求、已确认决定和项目已有规格。只有能改变本阶段行为的缺口才提出问题；代码和环境事实自行核查。UI 工作优先使用已有设计稿，不为没有设计稿的后端任务增加询问。

修订现有文件优先于创建副本。没有路径约定时使用 `specs/<feature-id>/PRODUCT.md`；标识从已知工单或特性名获得。没有工单也能写，不自动创建工单。

## 写出行为

用简短场景解释动机与使用方式，再用稳定的 `R-01` 等编号描述关键要求。写清条件、动作与可观察结果，覆盖本次变化涉及的正常、错误、取消、重试或并发情形。只保留与风险有关的情形，不穷举整个产品。

内部算法和模块布局放技术设计；协议字段、API 响应等外部契约可以在此定义。要求本身可检验，具体测试方法不在这里重复展开。

区分已确认行为与拟议行为。无法决定的问题放在相关要求附近，说明它阻塞什么；不要替用户或负责人发明答案。不把估计写成测量值，不用空泛品质词代替行为。

## 交付

保存请求的草案或修订，说明范围、重要变化和仍阻塞的决定。批准状态只能来源于明确确认。单纯写规格不启动实现。

已有批准且请求继续实现时，将本文件作为依据传递，不重置授权。需求变更时保留变更原因；不删除要求来掩盖未实现行为。
