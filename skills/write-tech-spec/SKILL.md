# Write tech spec

交付可评审的设计，说明相对现状改变什么、为什么，以及如何验证。

首次使用本库且尚未读取同版时，读取 [任务边界](references/operating-contract.md)。写作按需读取 [约定](references/technical-writing.md)；新文档使用 [模板](assets/TECH.template.md)，粒度参考 [示例](references/example-tech.md)。

## 调查后设计

先读取已有行为依据与受影响代码，确定入口、状态所有者、调用关系和关键约束。只调查相关区域。重要证据记录文件、符号和调查 commit；外部标准记录版本与条款。无法确认的事实保留为未知。

已有需求足够明确时不强制另写 PRODUCT。局部明确修改可跳过 TECH。确实需要实验才能决定时，优先提出或执行已授权的隔离原型；没有运行条件也可以交付标有缺口的草案。

沿用项目路径；没有约定时保存为 `specs/<feature-id>/TECH.md`，与已有行为规格使用同一标识。

## 内容

Context 只描述决定本次设计的现状和约束。Proposed changes 解释模块职责、接口、数据流、状态与所有权如何改变；按实际风险说明取消、失败、清理、兼容性和恢复。不要重新罗列全部仓库。

用具体场景论证真实取舍，包括不做的后果；没有合理替代方案不凑数。行为要求通过编号或明确段落引用，不复制成第二份需求。重大而持久的选择可以建议提取 ADR，默认仍是提案。

Testing and validation 将关键要求对应到具体测试、实验或人工步骤。写清设置、观察与失败条件，区分拟执行和已执行；将硬件/环境覆盖缺口显式列出。临时分工、分支和子 Agent 配置不进入长期设计正文。

## 交付

给出设计、关键证据、代价和未决问题；不自行标记批准。只有当前请求已经包含实施授权，且所需重大决定已明确，才继续实施。

实现阶段改变模块边界或约定时提交设计修订；纯定位信息、已确认事实可同步修正。保持理由与实际交付对应，不为消除差异而改弱行为契约。
